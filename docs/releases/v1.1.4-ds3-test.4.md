## Changes

- Open an independent DS3 control handle for the F2/F5 feature requests and
  deferred LED configuration. USB_FS input remains on its own handle.
  This follows the two-handle arrangement in
  [FreeBSD's libusb transport](https://github.com/freebsd/freebsd-src/blob/releng/9.3/lib/libusb/libusb20_ugen20.c),
  which explicitly separates control and interrupt transactions for kernel locking.
- Verify the second handle's VID/PID before sending any controller requests.
- For the known `054c:0268` DS3 only, query and detach an attached kernel driver
  before starting USB_FS. A successful `USB_CLAIM_INTERFACE` alone does not
  establish exclusive ownership in upstream FreeBSD. Detachment failure stops
  initialization; an unavailable query is logged and does not attempt detachment.
- Keep HID interface numbers distinct from FreeBSD kernel interface indices,
  including nonconsecutive numbers and alternate settings.
- Close the control handle on setup failure, shutdown and transport loss.
  Recovery recreates and verifies both handles while retaining its virtual user.

These changes correct the transport arrangement and driver ownership handling.
They have not yet been verified with the reporter's DS3 on PS5 firmware 11.40;
the precise cause of his ENXIO failures remains unconfirmed.
The normal release remains v1.1.3.

## Test

1. Stop test 3 and load this release's `LibrePadPS5.elf`. For Payload Manager,
   replace the ELF and JSON together. Confirm `1.1.4-ds3-test.4` in the dashboard.
2. Reconnect one DS3 and press its physical PS button. If it appears in the
   dashboard, use **Reconnect** if released and assign its separate PS5 user.
3. Move both sticks and press buttons for 30 seconds, then attach a fresh
   diagnostic report. The new control-handle and kernel-driver logs identify
   whether setup reaches the F2/F5 requests and starts receiving input.
